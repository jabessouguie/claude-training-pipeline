Atelier 3 — Votre premier prototype cliquable

Du texte à l'écran : transformer une spécification en prototype interactif

Durée

60 minutes (45 min de travail + 15 min de démo croisée et débrief)

Niveau

Intermédiaire (aucune compétence en code requise)

Format

Binôme (mêmes binômes que le matin)

Prérequis

Mini-PRD et user stories de l'exercice 2 · slides 2 à 6 et 15 du M2 (Generative UI, démo, prototype ≠ produit)

Matériel

Copilot · Bloc-notes (ou VS Code) · navigateur Edge/Chrome · en secours : assets/fil-rouge-stockpilot/atelier-3/prototype-fallback.html

Contexte

Votre mini-PRD StockPilot est prêt. Avant d'engager l'équipe de développement, vous voulez faire réagir le métier sur du concret : un prototype cliquable des trois écrans clés. Vous n'avez ni designer, ni développeur, ni licence Figma — seulement Copilot, un éditeur de texte et un navigateur. C'est suffisant.

Objectif

Vivre le réflexe « montrer plutôt que décrire » : transformer une spécification en prototype interactif par simple description en langage naturel, puis itérer dessus comme on itérera en réunion métier. Comprendre en le faisant pourquoi le coût du prototype s'est effondré — et ce que ça change à la conversation produit.

Consigne

  1. Générez : demandez un prototype d'application web en un seul fichier HTML (CSS et JavaScript inclus dans le fichier), avec 3 écrans navigables : recherche de matériel (avec filtres type/distance), fiche équipement (statut, localisation, historique), écran de réservation (dates, confirmation). Fournissez votre mini-PRD comme contexte. Exigez des données d'exemple réalistes (transpalettes électriques, scanners d'inventaire, chariots de réassort…).
  2. Sauvegardez et testez : copiez l'intégralité du code dans le Bloc-notes, enregistrez sous stockpilot.html (attention : pas .txt), ouvrez le fichier dans votre navigateur. Parcourez les 3 écrans.
  3. Itérez — au moins 2 fois : demandez des modifications en langage naturel. Obligatoire : (a) une amélioration visuelle ou de libellé (« les statuts en pastilles de couleur », « vocabulaire magasin, pas vocabulaire informatique ») ; (b) un cas d'erreur (« si le matériel est déjà réservé, afficher les prochaines disponibilités »). À chaque itération : re-sauvegarder, recharger, re-tester.
  4. Testez le rendu mobile : F12 dans le navigateur → mode responsive → format téléphone. Notez ce qui casse. (Si F12 est bloqué sur votre poste : réduisez simplement la largeur de la fenêtre du navigateur à celle d'un téléphone — le prototype étant responsive, l'effet est le même.)

Critères de réussite

  • Votre fichier stockpilot.html s'ouvre dans le navigateur et les 3 écrans s'enchaînent par de vrais clics.
  • Vous avez réalisé au moins 2 itérations dont un cas d'erreur visible dans le prototype.
  • Le prototype reflète VOS choix du matin (vocabulaire, périmètre V1, non-objectifs respectés — pas de géolocalisation temps réel si vous l'aviez exclue).
  • En démo croisée, un autre binôme comprend le parcours sans que vous l'expliquiez.

Indices — à consulter seulement si vous êtes bloqués

  1. Le résultat est du texte au lieu d'une app ? Vérifiez l'extension du fichier : il doit se terminer par .html, pas .html.txt (dans le Bloc-notes : « Type : Tous les fichiers » à l'enregistrement).
  2. Le code généré s'arrête en plein milieu ? La réponse a été tronquée : demandez « continue exactement où tu t'es arrêté, sans rien répéter », puis recollez bout à bout. Ou régénérez écran par écran : « donne-moi d'abord uniquement l'écran de recherche ».
  3. L'itération a cassé le prototype ? Demandez : « redonne-moi le fichier COMPLET incluant la modification » — l'IA a probablement fourni seulement le fragment modifié. En dernier recours, repartez de prototype-fallback.html et itérez dessus.

Bonus (binômes rapides)

Ajoutez le parcours « signalement de panne avec photo » issu de votre US de l'exercice 2 (le champ photo peut être simulé). Puis testez la démo d'avant-vente : l'un de vous joue le responsable logistique sceptique, l'autre pilote le prototype en argumentant.
